# Undo 與後續多人連線交接

## 目前行為

- 我方回合：Undo 撤回目前回合上一個已確認決策，可連續撤回；未確認的預放優先取消。
- 對方回合：只能提出悔棋請求，不能直接呼叫正常 Undo 跨過對方的動作。接受後回到交棒前最後一個我方決策，再可連續撤回該回合。
- AI 對練：送出確認後由 AI 介面自動接受。多人連線的傳輸、登入及雙方通知尚未串接。
- 開局擲骰及已結束對局不提供 Undo；重新開局／返回選單會清除撤回歷史。
- 固定 seed，紀錄雙方決策並重播到撤回點。抽牌／洗牌／擲骰不重抽；場地、Guts、棄牌、局數、效果及紀錄一起還原。

## 模組介面

`undo-tools.js` 的 `UndoSession` 管理同一個權威對局。`engine.js` 只新增 `turnNo` 作為邊界標記。

- `new UndoSession(engine, options)`：現有 UI 使用 human / ai；後續主機可用 `agents: [player0, player1]`，兩個真人 agent 都設 `wantsAck: true`。`localPlayer` 可為 0 或 1；線上必須提供同一個權威 `gameId`。
- `status(player)`：該玩家是否可撤回、目前是否對方回合，以及目標決策索引。
- `undo()`：只接受目前 `localPlayer` 自己回合的普通撤回。
- `requestTakeback(player)`：建立請求並暫停對局，回傳 `{id, gameId, requester, responder, revision, target, turn}`；同時最多一個待處理請求。
- `resolveTakeback(id, responder, accepted)`：只接受指定對手對同一個仍有效請求的布林回覆。接受就還原，拒絕就繼續；重複、過期或回應方不符會回傳 false。
- `cancelTakeback(id, requester)`：發起方取消，原對局繼續。
- `stop()`：使舊 AI／真人回呼失效。重播也會換掉整個引擎實例，避免舊的 Promise 或延遲回呼改寫新局。

## 多人版必須接上的部分

1. 由受信任主機保存 seed、完整決策紀錄與唯一版本；玩家操作先驗證回合與狀態版本，再提交。
2. 由已驗證連線身分取得玩家索引，不相信客戶端傳入的 requester / responder。此模組做對局一致性檢查，不取代伺服器身分驗證。
3. 悔棋請求送達對手，顯示接受／拒絕；主機鎖住該版本的後續操作。取消、逾時或斷線的解除方式由連線層處理，避免一直暫停。
4. 只有主機可以核准還原並產生新版本。雙方各接收同一新版本、各自可見的狀態，再繼續操作；勿只讓發起者本機回退。
5. seed、完整牌庫／手牌與完整決策紀錄保留在權威主機，不能為了客戶端重播而把對手隱藏資訊發給另一方。客戶端只接收其應可見的局面。
6. 現有 Firebase 多人專案使用不同遊戲引擎；本次未將兩套引擎合併，之後需另做 agent／網路狀態介面對接。

### 回合展示通知與 Loss 確認
- 引擎的 onNotice 是可等待的公開流程展示，不構成玩家決策；UndoSession 重播時略過，取消舊對局時同時取消其等待。UI onGame 必須清除舊提示，不可讓舊確認按鈕推進新對局。
- 真人的強制失分先由 lossConfirm 決策確認，之後才展示 Loss 結果、補牌與換發球；該決策會進入同一版本紀錄，可在確認畫面 Undo。
- 目前是本機 AI 對練流程。之後多人傳輸需由主機決定失分及回合版本；展示畫面的閱讀確認不能替代主機驗證，也不能把某端關閉提示當作新的牌局操作。
